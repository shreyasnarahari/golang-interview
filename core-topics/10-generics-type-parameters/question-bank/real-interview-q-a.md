# Topic 10 Real Interview Q&A

### Q: (Asked at a cloud infra company) "We have `type UserID int` everywhere. Our generic `func Clamp[T int | float64](v, lo, hi T) T` rejects it. Explain what's going on and what you'd change."
**Frequency**: often
**Why interviewers ask**: Real codebases are full of defined types with underlying primitives, and this tests whether you can debug a constraint failure under pressure.
**Answer**: `int` in a constraint matches only the predeclared `int`, so `UserID` — a defined type whose underlying type is `int` — is excluded from the type set. The fix is the underlying-type approximation operator: `~int` matches `int` *and* every type whose underlying type is `int`. So `Clamp[T ~int | ~float64]` accepts `UserID`, `time.Duration`-style types, etc. Two subtleties worth volunteering: (1) inside `Clamp`, `T` values support `<`/`>` because every member of the type set does, and the result stays `UserID`, preserving the caller's type; (2) `~` only widens *operations*, not methods — you cannot call `UserID`'s methods on a `T` value unless the constraint interface declares them.
**Follow-ups**: When would you intentionally keep `int` without `~` (e.g. bit-level algorithms where underlying-type semantics matter)? What if the function also needs to call a `String()` method on `T` — how do you combine that with the union?

### Q: (Asked at a systems/database company) "Why can't you write `func (t *Table[K]) Index[V any](...) Index[K, V]` — i.e. a method with its own type parameter — and what would you do instead?"
**Frequency**: sometimes
**Why interviewers ask**: Anyone who has built generic libraries hits this wall; the interviewer wants the *reason*, not just "the spec says no".
**Answer**: Go's spec prohibits type parameters on methods: methods may only use the receiver type's parameters. The root cause is Go's compilation strategy — generic code is stenciled at compile time by gcshape (one body per memory/GC-layout class, with a runtime dictionary), while interface method sets must be fixed at compile time so method tables can be built. A generic method would make a type's method set depend on future instantiations unknown at its declaration site, forcing runtime code generation or runtime interface-table construction, both of which the designers rejected. The idiomatic workaround is a top-level generic function: `func IndexOf[K comparable, V any](t *Table[K], f func(K) V) Index[K, V]`. This is why `slices`, `maps`, and the Go 1.23 `iter` helpers are all functions, not methods.
**Follow-ups**: How would you design the API so it still *feels* method-like (functional options, helper types)? Does this limitation affect interface satisfaction for generic types?

### Q: (Asked at a fintech company, senior loop) "A teammate proposes rewriting our `map[string]Position` caches as a generic `Cache[K comparable, V any]` and asks whether the generic version will be faster or slower than hand-written per-type code. What do you say?"
**Frequency**: sometimes
**Why interviewers ask**: It tests whether a senior engineer can tie language design (stenciling) to performance reasoning and API design trade-offs.
**Answer**: Mechanically, Go does not fully monomorphize: `Cache[string, Position]` and `Cache[*Key, Position]` share one stencil if their key/value gcshapes match (all pointer shapes share one body; `string` gets its own), with type-specific operations dispatched through a runtime dictionary. So a generic container is usually within a few percent of hand-written code, occasionally slower due to dictionary-indirect calls that resist inlining, and occasionally faster than `interface{}`-based designs because values are not boxed. But the real answer is that the decision should be made on API grounds: generics buy compile-time type safety (no assertions, no wrong-key bugs) and eliminate boxing; they cost nothing at runtime worth worrying about until a profile says otherwise. I'd also push back on rewriting working code for speed without a benchmark: measure with `testing.B` and `-gcflags=-m` to compare escape/inlining behavior before and after.
**Follow-ups**: Which specific operations in a generic container go through the dictionary (method calls on `T`/`V`, interface conversions, type switches)? When would the `interface{}`-based design actually be preferable (heterogeneous values, plugin boundaries, reflection-heavy code)?
