# Topic 11 Hard Questions

### Q: What is the `runnext` slot in a P, and what are its trade-offs?
**Frequency**: rare-senior
**Why interviewers ask**: It probes whether the candidate understands scheduler affinity optimizations beyond the basic queue model.
**Answer**: `runnext` is a 1-element high-priority slot on each P, checked before the local run queue. When a running goroutine G1 readies G2 (`go` statement, channel unblock), G2 lands in the P's `runnext`; if the slot is occupied, the evicted goroutine is pushed to the **tail of the local run queue**. Rationale: producer/consumer pairs often communicate next, so running G2 immediately preserves cache locality of the data G1 just touched. Trade-off: a ping-pong pair of goroutines (e.g., an unbuffered-channel rendezvous) can hog a P through `runnext`, starving the local queue. The runtime's guard is subtle: a `runnext` goroutine *inherits the current time slice* (`inheritTime` in `runqget`), so the pair still accumulates runtime on that slice and `sysmon`'s 10 ms preemption eventually breaks them up — and where `sysmon` doesn't exist (`haveSysmon == 0`, e.g., some ports), the runtime refuses to use `runnext` at all.
**Follow-ups**: Why does the evicted occupant go to the tail of the local queue rather than the global queue? How does `runnext` interact with work stealing?

### Q: Walk through what happens when a P's local run queue overflows its 256 slots.
**Frequency**: rare-senior
**Why interviewers ask**: Queue-capacity behavior is where the tidy GMP diagram meets the actual implementation in `runtime/proc.go`.
**Answer**: Each P's local run queue is a fixed ring buffer of 256 entries (`runq [256]guintptr`). When `runqput` finds it full, it moves **half the local queue plus the new goroutine** to the global run queue (`runqputslow`), keeping roughly the first half local for locality. Overflow is therefore amortized, not per-goroutine. The global queue is unbounded (a linked list) but contended — every access takes `sched.lock`, which is why the scheduler only consults it after local queues and why the 61-tick fairness check exists.
**Follow-ups**: Why move half the queue instead of just the one new goroutine? Why is the 256-entry fixed size preferable to a growable slice?

### Q: Why was SIGURG chosen for async preemption, and what does "safe point" mean here?
**Frequency**: rare-senior
**Why interviewers ask**: Signal-based preemption has subtle correctness constraints that only surface at the runtime level.
**Answer**: `SIGURG` is chosen because it is generated by default in ordinary programs (out-of-band socket data) yet almost never has a meaningful user handler, so stealing it doesn't break real applications — and unlike `SIGKILL`-adjacent choices it can be delivered spuriously without harm. A **safe point** is a program location where the goroutine's stack and registers are fully described by the compiler's stack maps, so the goroutine can be suspended, its stack scanned precisely by the GC, and resumed later. The signal handler (`asyncPreempt`) pushes an async preemption call only if the interrupted PC is at such a point; in tight assembly or runtime-critical sections the preemption is deferred.
**Follow-ups**: What happens if a goroutine is interrupted in a non-safe-point region like a write barrier? How does this differ from the cooperative stack-guard mechanism?

### Q: What are the costs and risks of changing GOMAXPROCS at runtime?
**Frequency**: rare-senior
**Why interviewers ask**: It exposes whether the candidate understands that P-count changes are a global stop-the-world operation, not a free knob.
**Answer**: `runtime.GOMAXPROCS(n)` triggers `procresize`, which **stops the world**, allocates or destroys P structures, redistributes runnable goroutines from destroyed Ps onto the global queue, then restarts. Frequent changes cause latency blips and destroy locality (goroutines lose their cache-warm P). Idle Ps aren't free either: each P owns scheduler state (mcache, timers, run queue), so wildly oversized values waste memory, and undersized values leave CPU idle. In containers, prefer the Go 1.25+ cgroup-aware default rather than calling it at all.
**Follow-ups**: Why might a service deliberately pin GOMAXPROCS below the core count (e.g., leaving headroom for GC or cgo threads)? What happens to goroutines on a P that gets destroyed?
