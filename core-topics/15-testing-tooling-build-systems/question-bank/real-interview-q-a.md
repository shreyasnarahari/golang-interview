# Topic 15 Real Interview Q&A

### Q: (Asked at a payments/fintech company) What is the Go race detector, how do you run it, and what are its limits?
**Frequency**: often
**Why interviewers ask**: Fintech code is heavily concurrent and correctness-critical; they want someone who treats races as a CI discipline, not a one-off debugging tool.
**Answer**: A runtime detector (ThreadSanitizer-based, built into the toolchain) that instruments memory accesses and reports any pair of unsynchronized accesses to the same location where at least one is a write. Run it with `go test -race ./...`, `go build -race`, or `go run -race`. In practice: enable `-race` on every CI test run, because it has essentially no false positives — a reported race is a real bug. The limits: it adds roughly 5–10× memory and 2–20× CPU overhead, so never in production binaries; it only catches races on code paths actually executed, so race detection quality tracks test coverage; and it needs a 64-bit supported platform. A strong answer adds: fixes should restore a happens-before edge (mutex, channel handoff, `sync/atomic`) rather than sprinkling `atomic` everywhere, and a failing `-race` CI job should block merge like a failing test.
**Follow-ups**: A `-race` run reports `WARNING: DATA RACE` with two stack traces — how do you read it? (previous access + current access + goroutine creation stacks) Why is "it passed under -race once" not evidence of race-freedom?

### Q: (Asked at a health-tech company with mandated coverage gates) How do you generate code coverage in Go, and why isn't 100% coverage the goal?
**Frequency**: sometimes
**Why interviewers ask**: Regulated industries impose coverage thresholds; they want candidates who can operate the tooling and who understand coverage's blind spots rather than gaming the metric.
**Answer**: Unit-test coverage: `go test -coverprofile=coverage.out ./...` then `go tool cover -html=coverage.out` for the annotated source view, or `go tool cover -func=coverage.out` for per-function percentages. `-covermode` selects the counter: `set` (was the statement executed — default), `count` (how many times), `atomic` (count, race-safe, for parallel tests). Since Go 1.20 you can also measure *integration/binary* coverage: build with `go build -cover`, run the real binary against a test environment with `GOCOVERDIR` set, then merge with `go tool covdata`. Why 100% isn't the goal: coverage counts executed statements, not verified behavior — tests that execute code without asserting anything still score; it says nothing about error paths, concurrency interleavings, or boundary inputs; and chasing the number produces brittle mock-heavy tests. Sensible practice: gate on a floor plus *differential* coverage on changed lines in PRs.
**Follow-ups**: Which `-covermode` would you pick for a test suite run under `-race`, and why? How would you measure coverage of an end-to-end test that runs the compiled binary in Docker?

### Q: (Asked at a distributed-systems/database startup) How would you gain confidence that a concurrent cache implementation is correct?
**Frequency**: sometimes
**Why interviewers ask**: It is a realistic design-plus-testing question: they want a layered testing strategy, not "I'd write some unit tests."
**Answer**: Layer the techniques. (1) *Table-driven unit tests* for the sequential contract — get/set/delete/eviction edge cases — each case a `t.Run` subtest. (2) *Property checks via fuzzing* (`testing.F`, Go 1.18+): fuzz operation sequences and assert invariants — e.g. after `Set(k,v)`, `Get(k)` returns `v` unless an eviction intervened; `Len()` never exceeds capacity. Run `go test -fuzz=FuzzCache -fuzztime=5m` in nightly CI; crashers land in `testdata/fuzz` as permanent regressions. (3) *Race detector*: `go test -race` with a stress test where many goroutines hammer the cache — catches missing happens-before edges, and any report is a real bug. (4) *Deterministic concurrency testing* with `testing/synctest` (stable in Go 1.25): run the test inside a bubble with a fake clock so time-based eviction tests are instant and deterministic instead of `time.Sleep` flakes. (5) *Benchmarks* with the Go 1.24 `b.Loop()` idiom (replacing `for i := 0; i < b.N; i++`, which the compiler could partially optimize away) to catch performance regressions, plus `-shuffle=on` to expose accidental order dependence between tests.
**Follow-ups**: Why does `b.Loop()` give more trustworthy benchmark numbers than the classic `b.N` loop? What invariant would you fuzz for an LRU eviction policy?
