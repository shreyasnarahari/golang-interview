# Topic 15 Hard Questions

### Q: How does the race detector work internally, and what performance penalty does `-race` introduce?
**Frequency**: rare-senior
**Why interviewers ask**: Separates people who merely run `go test -race` from those who understand what it can and cannot catch and why it can't ship in production.
**Answer**: `-race` instruments every memory access and synchronization operation with calls into a ThreadSanitizer-derived runtime. Each goroutine carries a vector clock; the runtime maintains shadow memory recording which clock last read/wrote each word, and reports a race when two accesses to the same location (at least one a write) are not ordered by a happens-before edge (channel ops, mutex lock/unlock, `WaitGroup`, atomics all create edges). Cost per the official docs: **memory ≈ 5×–10×** and **CPU ≈ 2×–20×**, scaling with how memory- and sync-intensive the code is — so never ship `-race` binaries to production. Crucially, it only detects races on paths *actually executed* during the run (a race detector pass with low coverage misses races), but it has essentially **no false positives**: a reported race is real. Supported on 64-bit linux/darwin/windows/freebsd (amd64, plus arm64 and a few others on Linux); not available on 32-bit platforms.
**Follow-ups**: Why can two unsynchronized writes escape detection even under `-race`? Why does the detector have no false positives but plenty of false negatives?

### Q: How does Go resolve dependency versions (MVS), and how does it differ from npm/Cargo-style resolution?
**Frequency**: rare-senior
**Why interviewers ask**: Dependency resolution is where Go's module design is genuinely unusual; seniors are expected to reason about build reproducibility and version surprises.
**Answer**: Go uses **Minimal Version Selection**: starting from the main module's `go.mod`, it walks the requirement graph and selects, for each module, the *minimum* version that satisfies every requirement listed anywhere in the graph — the highest of the minimums, never a newer release. Consequences: (1) builds are reproducible without a lockfile because the algorithm is deterministic; `go.sum` only pins *cryptographic hashes*, not versions; (2) adding a dependency can never silently *upgrade* an unrelated module beyond what some requirement demands; (3) `go get -u` / explicit `go get mod@vX.Y.Z` raises a floor by editing the main `go.mod`. npm/Cargo instead run a satisfiability solver that typically picks the *newest* version allowed by each range, which needs a lockfile for reproducibility and permits "another package's range forced a downgrade/duplication" behaviors Go doesn't have. Debug with `go mod graph`, `go mod why -m`, and `go list -m all`.
**Follow-ups**: Why does Go not need a lockfile, and what does `go.sum` actually guarantee? What happens to the build list when you add a `require` for an older version than one already implied?

### Q: What is semantic import versioning — why must a v2+ module live at a `/vN` import path?
**Frequency**: rare-senior
**Why interviewers ask**: Major-version bumps are where Go module migrations go wrong in real codebases; the question tests whether the candidate understands the design rationale, not just the mechanics.
**Answer**: Go treats different major versions as *different modules*: `github.com/foo/bar` and `github.com/foo/bar/v2` have distinct import paths and can coexist in one build (a program may import both during a migration). Rationale: an incompatible API change must not silently break dependents through MVS, and Go deliberately encodes the breaking change in the import path so it is visible at every call site. Mechanics: at v2.0.0 the `go.mod` module line must be `module github.com/foo/bar/v2`; tags look like `v2.1.0`. v0 and v1 are exempt from the suffix. The escape hatch `+incompatible` versions exist for pre-modules repos tagged ≥ v2 that never adopted modules. Common migration strategies: keep a `v2/` subdirectory, or branch/retag; and be careful that the *first* v2 tag often ships with a wrong module path — the classic `invalid version: module contains a go.mod file, so module path must match major version` failure.
**Follow-ups**: What is a `+incompatible` version and when does it appear? How can a codebase depend on both v1 and v2 of the same library during migration?

### Q: What problem do Go workspaces (`go.work`) solve, and when should you *not* use one?
**Frequency**: sometimes
**Why interviewers ask**: Multi-module repos are common at scale; the question tests whether the candidate knows the 1.18+ workspace model versus abusing `replace` directives.
**Answer**: Before Go 1.18, developing across interdependent modules meant littering `go.mod` files with `replace ../foo` directives that you must never commit. A workspace fixes this: `go work init` + `go work use ./modA ./modB` creates a `go.work` file; while inside the workspace, the build list is the union of the listed modules, so local edits in `modB` are picked up by `modA` without any `replace`. `go work sync` propagates the workspace's resolved versions back into each module's `go.mod`, and `GOWORK=off` (or `go env -w GOWORK=off`) forces single-module mode. Caveats: a workspace only affects the machine it's on — consumers of your modules ignore it; CI/release builds must resolve versions from committed `go.mod`s (commit `go.work` only for application monorepos, not libraries); and the workspace union can resolve *different* versions than any individual module build, so still test modules standalone.
**Follow-ups**: How is `go.work` different from a `replace` directive? Why can a build pass in a workspace but fail after `GOWORK=off`?
