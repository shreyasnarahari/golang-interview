# Topic 12 Real Interview Q&A

### Q: (A cloud infrastructure company) "Our Go services in Kubernetes keep getting OOM-killed under traffic spikes even though pprof shows a modest live heap. Walk us through diagnosing and fixing this."
**Frequency**: often
**Why interviewers ask**: This is the canonical Go-in-containers incident; it tests GOMEMLIMIT/GOGC fluency plus the gap between "live heap" and "RSS".
**Answer**: Diagnosis: RSS includes far more than live heap — spans retained by the allocator, scavenged-but-not-released pages, goroutine stacks, and fragmentation — and the default `GOGC=100` lets the heap *double* before collecting, so a service sized to its live heap OOMs between cycles. Get evidence with `GODEBUG=gctrace=1` (goal vs. live heap), `runtime.MemStats` (`HeapInuse`, `HeapReleased`, `NextGC`), and a heap profile. Fixes, in order: (1) set `GOMEMLIMIT` below the cgroup limit — e.g. `debug.SetMemoryLimit()` to ~90% of it — so the GC paces against the container instead of the OOM killer; this replaced the old "memory ballast" hack. (2) Consider `GOGC=off` with the limit so cycles are purely memory-driven; the runtime caps GC CPU at ~50% to prevent thrash. (3) Reduce allocation churn (`sync.Pool`, buffer reuse, escape analysis) and set container CPU/memory requests consistently with GOMAXPROCS. Watch that the limit is *soft*: a single request doing a giant allocation can still blow through it.
**Follow-ups**: How do you prove the OOMs were GC pacing and not a genuine leak? (Compare live heap across cycles in `gctrace`; a leak grows the live-heap floor monotonically.) What changes if the workload is cgo-heavy? (cgo memory is invisible to GOMEMLIMIT.)

### Q: (A language-runtime team) "Why did Go choose mark-and-sweep over reference counting? Couldn't ARC like Swift's avoid GC pauses entirely?"
**Frequency**: sometimes
**Why interviewers ask**: It forces a first-principles comparison of memory management strategies rather than reciting that "Go has a GC".
**Answer**: Go uses a concurrent **tri-color mark-and-sweep** collector, not reference counting. The reasons: (1) **Cost model** — RC turns every pointer write (parameter passing, slice element copies, interface assignments) into an atomic count update; tracing GC pays cost proportional to *live* data, only during a cycle. For Go's pointer-heavy style, RC's per-write tax exceeds tracing's periodic tax. (2) **Cycles** — pure RC leaks cyclic structures and needs a cycle detector anyway (Python has one). (3) **Pauses are already solved** — Go's concurrent marking with the hybrid write barrier keeps STW to sub-millisecond levels, removing RC's main selling point. (4) **Throughput and simplicity for concurrency** — no count bookkeeping shared across goroutines. RC's real advantages (prompt destruction, no background CPU) matter less for Go's server workloads; where prompt release matters, Go uses explicit `Close()`/`defer` rather than destructor timing.
**Follow-ups**: How does Go handle cyclic garbage then? (Tracing handles cycles naturally.) What did Go 1.24's `weak` package and `runtime.AddCleanup` change about this trade-off?

### Q: (A low-latency trading firm) "We need p99.9 request latency under a millisecond. How much can Go's GC hurt us, and what levers do you pull before reaching for off-heap hacks?"
**Frequency**: rare-senior
**Why interviewers ask**: Latency shops probe whether you know GC pauses are small but *allocation-driven jitter* (assists, scavenging) is the real enemy.
**Answer**: Raw STW pauses are rarely the problem — typically tens to a few hundred microseconds per cycle, a few times per second. The real p99.9 killers are **mutator assists** (allocation-heavy handlers get drafted into marking mid-request) and allocator/scavenger jitter. Levers, in order: (1) **Drive allocation rate to near zero on the hot path** — reuse buffers, `sync.Pool` (knowing pools are dropped each cycle), preallocate slices/maps, keep escaping objects off the heap; this reduces both cycle frequency and assist work. (2) **Raise GOGC or set GOMEMLIMIT with headroom** to make cycles rare, since cycles that never happen can't assist. (3) Keep goroutine counts and stack depths bounded to shorten STW. (4) Pin GOMAXPROCS to allocated CPUs to avoid scheduling noise masquerading as GC latency. Measure with execution traces (`runtime/trace`) filtered for `GC`/`assist` regions, not just `PauseNs`. Only after all that consider arenas/off-heap, since they abandon memory safety tooling like the race detector's coverage.
**Follow-ups**: Why does `sync.Pool` interact with GC (items don't survive a cycle — acceptable for caches of scratch buffers, not for correctness)? How would you distinguish assist-induced latency from scheduler latency in a trace?
